## 已确认的关键决定

1. 先完成P0-A住宿闭环，再完成P0-B雪场/装备。
2. 一个订单可包含多间住宿以及多个其他商品/服务。
3. 套餐与单选项可混合结算，一张订单只支付一次。
4. 每个具体住宿、票务场次、缆车时段或装备租赁都有独立订单项/占用；失败时整单事务回滚。
5. 滑雪票资格和缆车时段容量独立。
6. 营地业务时区为 `Asia/Shanghai`；时间范围使用半开区间。
7. DAY_PASS由开放规则决定，种子默认09:00–18:00。
8. 待支付占用15分钟；不使用quoteToken。
9. 创建订单提交完整购物车和 `expectedTotal`，服务端重算；价格变化返回 `PRICE_CHANGED`。
10. 价格以资源基础价为基准，每日只应用一个最高优先级匹配规则。
11. 金额使用CNY、`numeric(12,2)`，API为十进制字符串。
12. 一期只支持整单取消/模拟整单退款；部分取消和部分退款延期。
13. 装备型号固定BULK或ASSET追踪模式。
14. P0使用文本核销码；QR图形为P1。
15. 系统角色为CUSTOMER/ADMIN；JWT 30分钟，无refresh token。
16. A：朱承威（24325352）；B：袁顺熙（24325311）。

## 多商品订单不变量

- `customer_order` 是唯一付款边界；一张订单只有一个应付总额。
- 每间住宿生成一个 `order_item` 和一个 `lodging_reservation`，因此可订多间且仍能使用具体资源排斥约束。
- 套餐不是第二套订单：`order_package`保存套餐成交快照，相关 `order_item` 通过外键归组。
- 单选订单项的 `order_package_id` 为空；套餐项非空。
- 订单总额 = 所有订单项成交小计 − 套餐优惠快照；不得为负。
- 创建订单按固定顺序锁定/占用全部资源，任何一项失败则整单回滚，不产生“半个购物车”。
- 支付成功确认全部订单项；v1取消整单释放全部尚未履约占用。
- 每个订单项有独立履约状态；订单状态是聚合结果，避免多日期商品共用一个模糊的IN_USE状态。
- 同一订单全部项目属于同一营地；只有全部明细尚未开始履约时允许顾客整单取消。

## 尚存风险

- 混合购物车增加锁顺序和事务时长，必须通过固定锁顺序及并发测试验证。
- 套餐固定总价如何分摊到各订单项关系到退款；v1不做部分退款，仍需保存可解释分摊快照以支持报告。
- 多间房同单需要验证同一 `resource_unit_id` 不能在请求中重复，并对所有住宿逐项保存价格快照。
- 成员B已具备 `write` 权限并在 PR #1 中完成真实 Approve；但该 Review 正文仅一个词，未对 D-001 的服务层完整性、D-002 的调度语义、R5-04 等被点名的风险逐项表态。冻结按“无 Request changes”成立，实现阶段仍需以测试而非 Review 意见兜底。
- `D-001` 已批准方案B（允许全营地住宿模式价格规则）；`D-002` 已批准方案A（后端定时扫描逾期租赁）；`D-003` 确立 `OccupancyStatus`；`D-004` 确立核销部分唯一索引；`D-005` 允许 `price_rule` 的资源类型与住宿模式同时为空。五项均已进入 v1.0。

## 契约修改流程

1. 从最新 `develop` 创建 `docs/contract-<topic>` 或对应feature分支。
2. PR说明原因、兼容性、迁移、API/DTO/前端/测试影响。
3. 另一成员明确批准；共享表变化不得口头跳过审查。
4. 同步修改数据库契约、API、枚举、Flyway、Java DTO、TypeScript类型、测试和CHANGELOG。
5. 在干净数据库和真实PostgreSQL集成测试通过后合并。
6. 在本文件追加版本记录，不删除旧决策。
