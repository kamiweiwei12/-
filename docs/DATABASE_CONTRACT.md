# 数据库公共契约

状态：`DRAFT v0.1`，**不是可直接执行的最终迁移**。

## 1. 全局规则

- PostgreSQL 为唯一权威数据库；schema 暂定 `public`。
- 主键 `bigint generated by default as identity`；API 中ID按字符串传输，避免JS精度问题。
- 金额 `numeric(12,2)`，币种固定 `CNY`；数量 `integer CHECK (quantity > 0)`。
- 时刻 `timestamptz`，业务日期 `date`；范围统一 `[start_at,end_at)`。
- 软停用优先于删除。存在交易历史的用户、资源、价格规则不得级联删除。
- 所有表至少有 `created_at`；可变主数据另有 `updated_at`。

## 2. 候选关系模式

### 身份与权限

```text
app_user(user_id PK, email UQ, password_hash, display_name, phone, status, created_at, updated_at)
role(role_id PK, code UQ, name)
user_role(user_id PK/FK, role_id PK/FK, granted_at)
```

一期只有 CUSTOMER/ADMIN，但保留规范化角色表以支持权限演示。

### 营地、季节与住宿资源

```text
campground(campground_id PK, code UQ, name, timezone, currency, status, ...)
season(season_id PK, campground_id FK, code, name, start_date, end_date, UQ(campground_id, code), CHECK end>=start)
resource_type(resource_type_id PK, campground_id FK, code, name, kind, base_capacity, base_price, ...)
resource_unit(resource_unit_id PK, resource_type_id FK, code, name, capacity, status, UQ(resource_type_id, code))
resource_type_stay_mode(resource_type_id PK/FK, stay_mode PK)
resource_open_rule(open_rule_id PK, resource_unit_id FK, valid_from, valid_to, weekday, open_time, close_time, is_open, priority)
resource_maintenance(maintenance_id PK, resource_unit_id FK, period tstzrange, status, reason, ...)
```

`season` 只是日期分类；不能作为全局模式开关。

### 价格

```text
holiday(holiday_id PK, campground_id FK, holiday_date, name, UQ(campground_id, holiday_date))
price_rule(price_rule_id PK, campground_id FK, resource_type_id FK NULL,
           stay_mode NULL, rule_type, operation, value, priority,
           valid_from, valid_to, enabled, description)
price_rule_weekday(price_rule_id PK/FK, weekday PK CHECK 1..7)
price_rule_date(price_rule_id PK/FK, service_date PK)
```

规则匹配：先筛选营地、资源类型/住宿模式、有效期、星期/日期；`MANUAL_OVERRIDE/SPECIAL_DATE/HOLIDAY/SEASON/WEEKEND/BASE` 依次降低默认优先级，实际用 `priority` 决定。为避免组合不确定：

- 同一优先级只允许一个 `FIXED` 规则。
- 先选择最高优先级 `FIXED` 作为基价；再按优先级应用明确标记可叠加的 `MULTIPLIER/ADDITION`。
- 第一版建议每个计费日只采用一个胜出规则，降低解释和测试成本；是否允许叠加列为确认项。

### 统一订单、支付与历史

```text
customer_order(order_id PK, order_no UQ, user_id FK, campground_id FK,
               status, currency, total_amount, expires_at, version, created_at, updated_at)
order_item(order_item_id PK, order_id FK, item_type, item_name_snapshot,
           quantity, unit_price, subtotal, price_explanation jsonb)
order_status_history(history_id PK, order_id FK, from_status, to_status, changed_by FK NULL, reason, changed_at)
payment(payment_id PK, order_id FK, payment_no UQ, status, amount, method='SIMULATED', idempotency_key UQ, paid_at, created_at)
price_snapshot_line(snapshot_line_id PK, order_item_id FK, service_date, rule_id FK NULL,
                    rule_name_snapshot, operation_snapshot, rule_value_snapshot, amount)
```

约束：`subtotal = quantity * unit_price` 只适用于简单项；住宿逐日合计以 `price_snapshot_line` 汇总并在服务层/过程校验。订单金额不得由客户端写入。

### 住宿/日营占用

```text
lodging_reservation(reservation_id PK, order_item_id UQ/FK, resource_unit_id FK,
                    stay_mode, stay_period tstzrange, guest_count, occupancy_status)
```

有效占用使用部分排斥约束：

```sql
EXCLUDE USING gist (
  resource_unit_id WITH =,
  stay_period WITH &&
)
WHERE (occupancy_status IN ('PENDING_PAYMENT','CONFIRMED','IN_USE'));
```

需要 `btree_gist`。订单状态和占用状态不能靠两个任意更新入口维护；业务过程在同一事务同步，触发器仅记录历史/阻止非法不变量。

### 滑雪票、课程、缆车和核销

```text
ski_product(ski_product_id PK, campground_id FK, code UQ, name, product_kind, base_price, status)
ski_session(ski_session_id PK, ski_product_id FK, start_at, end_at, capacity, reserved_quantity, status,
            UQ(ski_product_id, start_at), CHECK reserved between 0 and capacity)
ski_booking(ski_booking_id PK, order_item_id UQ/FK, ski_session_id FK, quantity)
lift(lift_id PK, campground_id FK, code UQ, name, status)
lift_slot(lift_slot_id PK, lift_id FK, start_at, end_at, capacity, reserved_quantity, status,
          UQ(lift_id, start_at), CHECK reserved between 0 and capacity)
lift_booking(lift_booking_id PK, order_item_id UQ/FK, lift_slot_id FK, quantity)
verification_token(token_id PK, order_item_id FK, token_hash UQ, status, valid_from, valid_until)
verification_event(event_id PK, token_id FK, lift_slot_id FK NULL, result, verified_at, operator_id FK NULL)
```

容量事务锁定 `ski_session`/`lift_slot FOR UPDATE`，检查后原子递增。取消按业务占用记录精确递减并写流水/历史。

### 装备、资产、维修与库存流水

```text
equipment_model(model_id PK, campground_id FK, code UQ, name, tracking_mode, rental_price, deposit_amount, status)
equipment_stock(stock_id PK, model_id UQ/FK, total_quantity, maintenance_quantity,
                CHECK 0<=maintenance<=total)
equipment_asset(asset_id PK, model_id FK, asset_code UQ, status, acquired_at, retired_at NULL)
equipment_rental(rental_id PK, order_item_id UQ/FK, model_id FK, rental_period tstzrange,
                 quantity, status, picked_up_at NULL, returned_at NULL)
equipment_rental_asset(rental_id PK/FK, asset_id PK/FK)
equipment_maintenance(maintenance_id PK, asset_id FK, period tstzrange, status, description, cost NULL)
inventory_movement(movement_id PK, model_id FK, asset_id FK NULL, order_item_id FK NULL,
                   movement_type, quantity, occurred_at, operator_id FK NULL, note)
```

- ASSET 模式：`equipment_rental_asset` 对有效租期建立资产+时间排斥（可能使用单独 `asset_reservation` 表以允许部分条件）。
- BULK 模式：锁 `equipment_stock` 行，汇总重叠有效租赁数量；`available = total - maintenance - overlapping_reserved`，不把可用量作为独立真值列。
- 当前状态是便捷投影，库存流水不可变，用于解释每次变化。

### 天气与统计（P1/视图）

```text
weather_alert(alert_id PK, campground_id FK, severity, start_at, end_at, title, message, active)
```

视图候选：`v_daily_revenue`、`v_resource_occupancy`、`v_equipment_availability`、`v_lift_slot_traffic`、`v_order_summary`。

## 3. 3NF与必要冗余

- 类型、具体资源、支持模式分表，消除资源名称和类型属性的传递依赖。
- 订单与多类业务用 `order_item` + 专属占用表分解，不在订单表保存多组可空资源字段。
- 价格规则星期/指定日期使用关联表，不保存逗号字符串。
- 角色与用户多对多分解；装备型号与具体资产分解。
- `reserved_quantity`、资产当前状态属于可重建的性能投影，必须由事务维护并与业务记录核对。
- 名称、金额、规则解释在订单中有意快照，属于历史审计需要，不要求随主数据更新。

## 4. 索引候选

- `customer_order(user_id, created_at desc)`；活跃订单部分索引。
- `lodging_reservation` 的 GiST 排斥索引同时支持冲突查询。
- `price_rule(campground_id, resource_type_id, valid_from, valid_to, priority desc)`。
- `ski_session(ski_product_id, start_at)`、`lift_slot(lift_id, start_at)`。
- `equipment_rental(model_id)` + GiST `rental_period`；外键按查询需求补索引。
- 所有索引必须用真实数据和 `EXPLAIN (ANALYZE, BUFFERS)` 验证，不预设性能结论。

## 5. 数据库高级特性映射

- 事务：创建/取消订单、容量占用、装备取还。
- 排斥约束：住宿和单件资产时间冲突。
- `SELECT FOR UPDATE`：容量和批量库存。
- 触发器：订单状态历史、库存流水审计（不代替用例编排）。
- 函数/过程：报价、创建占用、取消释放的数据库核心原语。
- 视图：每日收入、入住率、装备可用、缆车流量。

## 6. 未决数据库问题

1. 一张订单一期是否严格只允许一个住宿项。
2. 价格规则是否允许倍率叠加；建议 v1 单规则胜出。
3. 待支付占用有效期建议15分钟，是否确认。
4. DAY_PASS 默认时段（建议09:00–18:00）是否按资源配置。
5. 批量装备是否允许同一型号同时存在部分单件追踪；建议一个型号固定一种 tracking_mode。
